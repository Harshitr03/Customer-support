# Design: AI Support Agent for @SpotifyCares (Hiver take-home)

## Overview

Build an AI support agent for the `SpotifyCares` brand from the Kaggle
"Customer Support on Twitter" dataset. The agent, given an incoming
customer message, must: (1) classify intent, (2) draft a reply grounded in
how Spotify has historically resolved similar issues, (3) decide
auto-handle vs. escalate with a stated reason. Deliverable is a runnable
repo + golden eval set + eval harness + report + decision log, per the
assignment brief.

## Goals / non-goals

**Goals**: a working, inspectable pipeline; an honest evaluation against
two baselines; a golden set the author can defend live; a report that is
upfront about what the headline numbers hide.

**Non-goals**: production-grade infra (no queues, no retries-with-backoff
service, no multi-brand generalization), fine-tuning a model, using the
full 3M-row dataset, building a UI.

## Brand & scope

`SpotifyCares` (~43k outbound tweets). Rejected `AmazonHelp` /
`AppleSupport` (too broad — would blow up the intent taxonomy) and
airline brands (replies are mostly "please DM us," too canned to ground
generation on). Spotify's issues cluster into a tractable set: app bugs,
account/login, billing, content/catalog, cancellation, feature
complaints — confirmed by manual sampling of 6 threads during
brainstorming.

## Data pipeline

1. Parse `data/raw/twcs/twcs.csv` (3M rows, `tweet_id, author_id, inbound,
   created_at, text, response_tweet_id, in_response_to_tweet_id`).
2. Reconstruct threads by following `in_response_to_tweet_id` /
   `response_tweet_id` chains.
3. Filter to threads containing at least one `SpotifyCares` outbound
   tweet.
4. For each thread, extract: customer's opening message, full turn
   sequence, and Spotify's reply turns.
5. Randomly sample a working pool of ~6,000 threads (fixed seed) for
   speed and reproducibility — full 43k not needed and the assignment
   explicitly expects subsampling.
6. Split the pool 90/10 into `corpus_pool` (historical KB + baseline
   training) and `eval_pool` (source for the golden set), disjoint by
   thread, so retrieval is never grounding a message from the test set
   against itself.
7. Cache all intermediate artifacts under `data/interim/` (gitignored,
   regenerated by the pipeline, not committed).

## Intent taxonomy

Derived from data, not assumed. Process: read a stratified sample of
~150 threads from `corpus_pool`, cluster into categories, converge on
6–8 intents. Working hypothesis to validate against real sampling:
`playback_bug`, `account_login`, `billing_subscription`,
`content_catalog`, `cancellation_refund`, `feature_complaint`, `other`.
Final taxonomy + definitions + example utterances go in
`src/support_agent/taxonomy.py` as the single source of truth used by
both the classifier prompt and the golden-set labeling rubric.

## Retrieval / grounding (RAG)

- Embed each `corpus_pool` thread's customer message with a Gemini
  embedding model; store vectors as a `.npy` matrix + metadata parquet
  under `data/interim/kb/` (gitignored, rebuilt on first run, cached
  after).
- At inference time: embed the incoming message, cosine-similarity
  top-k (k=3–5) against the corpus, pass those (customer msg, Spotify
  reply) pairs into the reply-drafting prompt as grounding examples.
- No vector DB — numpy cosine search is plenty at this scale (≤6k
  vectors) and keeps the dependency footprint small and the pipeline
  inspectable.

## Classification

Three systems compared on a common held-out test fold of the golden
set (see Eval harness):

- **Trivial baseline**: majority-class predictor.
- **Simple baseline**: TF-IDF + logistic regression, trained on a small
  labeled train fold carved out of the golden set (since we don't have
  a separate large labeled training set — flagged explicitly as a
  limitation, see Report).
- **Main approach**: Gemini few-shot classification, taxonomy +
  examples in-prompt, no training data needed beyond the few-shot
  examples embedded in the prompt.

## Reply drafting

Gemini call conditioned on: customer message + predicted intent +
top-k retrieved historical (message, resolution) pairs. Baselines for
reply quality, evaluated on the same test fold:

- **Trivial**: one generic canned reply per intent (e.g., "please DM us
  your account email").
- **Simple**: return the single nearest-neighbor historical reply
  verbatim, no generation.
- **Main approach**: grounded generation as above.

## Escalation policy

A small, auditable rule layer, not another opaque LLM judgment call:
escalate if intent is in a fixed escalate-by-default set (e.g. account
security/fraud, payment disputes, legal/safety language), OR
classifier confidence is below a threshold, OR the thread shows 3+
prior unresolved back-and-forth turns. Every decision returns a
human-readable reason string. Exact thresholds/intent set finalized
once the taxonomy and real confidence distributions are known, and
documented in the decision log.

## Eval harness

- **Golden set**: 150–250 examples stratified-sampled from `eval_pool`
  across the finalized intent taxonomy, manually labeled with (intent,
  escalate/auto label + reason, notes). Labeling methodology and
  sampling procedure documented in `eval/golden_labeling_notes.md`.
  Labeling in this take-home is done by the author (working with
  Claude as an assistant) rather than crowd-sourced — this is disclosed
  explicitly, and the README will flag which subset the user should
  spot-check before defending it live.
- **Split**: small train fold (~50–70 examples) carved from the golden
  set for the TF-IDF baseline's training data; remaining ~150–180 form
  the common test fold used to compare all classification/reply/escalation
  approaches apples-to-apples.
- **Automated metrics**: classification accuracy/F1 (all 3 systems),
  escalation precision/recall vs. gold labels.
- **LLM-as-judge**: Gemini scores each drafted reply 1–5 on a rubric
  (grounded-in-history, factually consistent, correct tone, actionable)
  with the rubric criteria spelled out in-prompt.
- **Judge/human agreement**: a subset (~40 examples) is independently
  scored by a human (the author) using the same rubric, blind to the
  judge's scores, and agreement (Cohen's kappa + correlation) is
  reported. This is the required "evidence the judge agrees with a
  human" — its limitations (single human rater, same person who tuned
  the system) go in the report's "what's misleading" section.

## Report & decision log

`report/REPORT.md` covers: problem framing (what "good" means for this
brand + what was deliberately not built), results vs. both baselines,
top-5 failure modes with real examples, the mandatory "what's
misleading about my headline number" section, and next-week plan.
`report/DECISION_LOG.md` is a flat bullet list of 10–15 non-obvious
decisions (e.g. brand choice, subsample size, train/test split of the
golden set, escalation thresholds) with the reasoning behind each.

## Reproducibility (< 15 min)

- Fixed random seeds throughout.
- LLM calls (classification, generation, judge, embeddings) are cached
  to disk keyed by input hash — first run pays API latency, reruns are
  near-instant.
- `scripts/run_demo.py` is the single entrypoint the README points at;
  it runs the full pipeline on the working pool (~6k threads, not the
  full 43k/3M) and prints the headline metrics table.
- README documents exact steps: env setup, API key, dataset location,
  one command to reproduce.

## Risks / limitations (seed list for the report)

- Golden set labeled by the author, not independently verified —
  possible unconscious bias toward labels the pipeline gets right.
- TF-IDF baseline trained on very few examples (~50–70) — not a fair
  fight, included anyway because the assignment requires a "simple"
  baseline and this is the honest state of available labeled data.
- LLM judge and generator share a provider (Gemini) — possible
  self-preference bias not fully ruled out by the human-agreement
  check on only ~40 examples.
- Single-brand, single-language (English) scope — no generalization
  claim.
